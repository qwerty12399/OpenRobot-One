# OpenRobot-One 多岗位仓库展示设计

## 1. 目标

将当前 GitHub 仓库整理为一套面向国内非开发岗位的统一项目作品集。仓库必须让 HR 在 30 秒内理解项目价值，让技术面试官在最多两次点击内找到可核验的实现、测试脚本或验证报告。

目标岗位分为四组：

1. 技术支持、FAE、售后支持；
2. 项目交付、项目实施；
3. 机器人系统测试、硬件测试；
4. 售前、技术销售，作为补充方向。

展示语言以中文为主，保留 ROS 2、STM32、SLAM、TF、CI 等通用英文技术名词。

## 2. 设计原则

- 统一项目事实，多岗位阅读入口，不为不同岗位复制多个仓库。
- 采用“岗位能力 → 项目行为 → 可核验证据”的表达方式，不使用无法验证的熟练度描述。
- 严格区分“实际通过”“静态检查”“未验证”，不把规划项写成已完成功能。
- README 服务快速判断，独立展示页服务深入核验。
- 只整理展示层、证据索引和仓库元数据，不修改机器人功能代码。
- 不创建没有实际内容的 Issues、Projects、Release 或演示材料。

## 3. 选择的方案

采用双层展示结构：

- `README.md`：面向 HR 和首次访问者，提供项目摘要、核心成果、岗位能力矩阵、架构、精选图片和证据入口。
- `docs/project_showcase.md`：面向技术面试官，提供验证状态、实测数据、测试环境、排障案例和交付物索引。

该方案比仅修改 README 更便于核验，又不需要在缺少完整演示视频时提前建设作品集网站、Release 或项目看板。

## 4. README 信息架构

README 按以下顺序组织：

1. 首屏项目定位：ROS 2 与 STM32 移动机器人集成、验证和交付；
2. 适配岗位：四类岗位入口和共同能力摘要；
3. 核心成果：ROS 2 工程基线、参数化模型、Gazebo/SLAM、STM32 H2、CI 与交付文档；
4. 能力矩阵：岗位能力、项目行为和证据链接；
5. 演示与证据入口：精选图片、展示页、验证报告和运行命令；
6. 系统架构：保留 Mermaid 架构，但降低视觉、LLM 等未完成模块的权重；
7. 验证状态：实际通过、静态检查、未验证；
8. 典型问题定位案例；
9. 工程结构与复现方式；
10. 路线图、限制和许可证。

首屏不得把视觉智能、LLM 或真机闭环描述为当前主要成果，因为这些模块仍处于工程骨架或待实现阶段。

## 5. 多岗位能力映射

| 岗位方向 | 重点能力 | 项目行为 | 主要证据 |
| --- | --- | --- | --- |
| 技术支持 / FAE / 售后 | 问题复现、串口联调、异常恢复、安全边界、客户文档 | 建立 H2 UART 验收、错误输入测试和硬件安全门 | 测试脚本、板级报告、协议和安全规范 |
| 项目交付 / 实施 | 需求拆解、阶段验收、接口统一、风险与文档管理 | 划分 H0–H4、统一 ROS 接口、维护路线图和验收标准 | 验收标准、路线图、Docker 和 CI |
| 机器人系统 / 硬件测试 | 自动化测试、边界测试、TF 检查、软硬件集成 | 执行 UART 压测、ROS 测试、Launch 和接口验证 | 自动化脚本、ROS 测试、验证报告 |
| 售前 / 技术销售 | 架构讲解、方案选型、约束说明、预期管理 | 记录架构、BOM、硬件事实和未验证边界 | 架构图、BOM、硬件事实、完成度表 |

## 6. 技术证据页

`docs/project_showcase.md` 包含以下内容：

- 项目角色和职责边界；
- 成果清单，每项记录状态、日期、环境和证据入口；
- STM32 H2 实测：`10000/10000` UART 往返、错误帧、超长帧、半包超时、错误波特率恢复和 `20/20` 复位重连；
- ROS 2 仿真、SLAM、TF 所有权和接口检查；
- 典型排障案例，统一使用“现象 → 假设 → 检查 → 结论 → 防复发”格式；
- 交付物索引：架构、协议、BOM、验收标准、测试脚本、验证报告和硬件手册；
- 当前限制和下一验证门。

所有数据必须链接到仓库中现有的脚本、报告或配置。没有当前证据的数据不进入成果表。

## 7. 视觉材料

- 从现有硬件图片中选择 3–4 张能够说明主控、通信和电机驱动方案的照片；
- 将精选副本放入 `docs/assets/showcase/`，使用清晰的英文文件名，保留原始图片不变；
- 保留 Mermaid 系统架构图；
- 没有真实仿真截图或演示视频时不生成容易被误认为实测的效果图；
- 后续获得真实录像后，再增加 60–90 秒演示入口和阶段 Release。

## 8. 仓库管理

- `main` 始终保持为可展示版本；
- README 展示 GitHub Actions、ROS 2、STM32 和 Apache-2.0 等必要徽章；
- 提交信息描述真实变更，不重写或伪造既有历史；
- GitHub 简介保持简洁，并补充 `ros2`、`stm32`、`robotics`、`slam`、`hardware-integration`、`technical-support` 等 Topics；
- 当前不创建空 Issues、Projects 或 Release；
- 真实演示视频和新的阶段验收完成后，再增加对应 Release 或演示入口。

## 9. 实施范围

计划修改或新增：

- 修改 `README.md`；
- 新增 `docs/project_showcase.md`；
- 新增 `docs/assets/showcase/` 下的精选图片副本；
- 在有可用 GitHub 授权能力时更新仓库简介和 Topics。

不修改 ROS 2、STM32 固件、测试脚本、Launch、配置或公开接口。

## 10. 验证

实施完成后执行：

1. 检查 README 和展示页中的相对链接与图片路径；
2. 检查每个成果指标均有对应证据链接；
3. 检查“实际通过、静态检查、未验证”状态用词一致；
4. 检查 Git 差异只涉及展示范围；
5. 推送后在未登录页面确认 README、图片、Mermaid 和徽章正常显示；
6. 核对本地与远端 `main` 提交一致且工作区干净。

本次不修改功能代码，因此不以 ROS 2 全量测试作为展示层变更的通过条件。若没有重新运行 ROS 2 测试，交付报告必须明确标注“本次未复验”，不得沿用旧结果声称当前构建通过。

## 11. 已知风险

- 当前缺少真实仿真录屏和整车运动视频，首版只能使用硬件照片、架构和验证报告；
- H3/H4 未完成，不能宣称电机控制、编码器反馈或闭环里程计已通过；
- GitHub 元数据更新依赖当前会话是否具备仓库管理授权；如果不可用，代码和文档仍可推送，但 Topics 需要在 GitHub 页面手动补充；
- CI 徽章会反映 GitHub Actions 的实时状态，不能人为声明成功。

## 12. 成功标准

- HR 在 README 首屏 30 秒内能理解项目、真实成果和适配岗位；
- 四类岗位均能在同一仓库中找到对应能力证据；
- 技术面试官最多两次点击即可打开测试脚本或验证报告；
- 所有量化指标均来自已有真实测试；
- 规划模块、未验证项和已通过项没有混淆；
- GitHub 公共页面的链接、图片、Mermaid 和徽章正常显示。

## 13. 后续步骤

规格经用户复核后，进入实现计划，再按计划修改 README、建立证据页、整理图片和更新仓库元数据。
